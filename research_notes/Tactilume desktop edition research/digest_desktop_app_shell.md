## Bottom line
- Electron 45 is the low-risk shell. It is the only web runtime with one Chromium engine on Windows, macOS and Linux, so WebGPU, the Gamepad API, WebHID and a Node HTTP/WebSocket server for the phone controller work everywhere, at ~121–158 MB compressed runtime. Tauri 2 loses WebGPU on Linux and on macOS before 26, and WebHID on macOS and Linux. An installable PWA cannot host the LAN server. Only native code (wgpu/SDL3, C++, engines) reaches hardware ray tracing and DLSS/XeSS-class upscalers, at the cost of rewriting the web codebase. Middle path: Electron for v1 with WebGPU plus the existing WebGL2 renderer as fallback; revisit native only if ray tracing or upscalers become requirements. [Inference]

## Security baseline
- Context isolation is the default since Electron 12 and the sandbox since 20; disabling context isolation also disables the sandbox. The 20-item checklist includes a restrictive CSP, custom protocols over `file://`, IPC sender validation, limited navigation and window creation, and checking fuses. https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/security.md [Verified]
- Validate `event.senderFrame` by origin, not URL; never pass `ipcRenderer.on` or raw callbacks through `contextBridge`; `file://` pages can read every local file. Same source. [Cited]
- Fuse defaults: `runAsNode`, `nodeOptions`, `nodeCliInspect`, `grantFileProtocolExtraPrivileges` and `wasmTrapHandlers` enabled; `cookieEncryption`, `embeddedAsarIntegrityValidation`, `onlyLoadAppFromAsar` and `loadBrowserProcessSpecificV8Snapshot` disabled. Turning off `runAsNode` makes `child_process.fork` throw. https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/fuses.md [Verified]
- `utilityProcess.fork()` gives a child with Node and MessagePorts through Chromium's Services API, callable only after `ready`; macOS options include `allowLoadingUnsignedLibraries` (leave off) and `disclaim`. https://raw.githubusercontent.com/electron/electron/main/docs/api/utility-process.md [Verified]
- Recommended baseline [Inference]: one sandboxed, context-isolated window with a typed preload API; app served from an `app://` protocol with CSP `default-src 'self'`; navigation and `window.open` denied; HID allowed only for gamepad usage pages; `runAsNode`, `nodeOptions`, `nodeCliInspect` and `grantFileProtocolExtraPrivileges` off, ASAR integrity and `onlyLoadAppFromAsar` on. The phone server runs in a `utilityProcess` and sends controller events to the renderer over a `MessagePort`.
- LAN hardening (general practice; Electron has no docs on this): listen only while pairing or in controller mode, per-session token in the QR URL, `Origin`/`Host` check on WebSocket upgrade, schema validation and rate limits, no LAN message reaches privileged IPC, phone page served by the same server. CSP needs for WASM and workers unverified.

## Phone-controller networking and OS prompts
- macOS 15+ Local Network privacy: listening for and accepting incoming TCP needs no access. Outgoing TCP, any UDP send, connecting a UDP socket, receiving multicast or broadcast, `.local` resolution and all Bonjour operations need it, through every API. No MDM control; identity is tracked by code signature and main-executable UUID; add `NSLocalNetworkUsageDescription`. Reset buttons arrive in macOS 27.2; macOS 15.5+ subnet exemptions help CI. Apps launched from Terminal are auto-allowed, so developers never see the prompt. https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy [Verified]
- Design consequence [Inference]: the desktop runs HTTP plus WebSocket and the phone connects in, so macOS shows no prompt. Pair with a QR code for `http://<LAN-IP>:<port>/?t=<token>`; no Bonjour/mDNS; no desktop-originated WebRTC or UDP (WebRTC mDNS candidates probably prompt, untested). Add the usage string anyway; no `disclaim: true` on the server process. Shared Electron executable UUIDs could confuse tracking of outgoing or UDP traffic (unverified).
- Windows: unsolicited inbound traffic blocked by default [Unverified]. Rules are per profile (`profile=private remoteip=localsubnet` style), and a Private-only rule doesn't apply on a network classified Public [Unverified: third-party guides]. The first-run "blocked some features" dialog, admin rights to allow, and block rules on cancel are recalled only.
- Windows plan [Inference]: an elevated per-machine NSIS install pre-creates a TCP, port-scoped, Private, local-subnet rule and removes it on uninstall; per-user installs can't, so users see the dialog. Detect "no phone after N seconds" and explain switching the network to Private.
- Linux: ufw and firewalld don't prompt per app; distro defaults unverified.

## Signing and notarization
- Apple Developer Program: 99 USD/year. https://developer.apple.com/programs/whats-included/ [Verified]. Notarization: `notarytool` or Xcode 14+ (altool rejected since 2023-11-01), Developer ID, Hardened Runtime, stapling. https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution [Verified]. Sequoia removed the Control-click Gatekeeper override. https://developer.apple.com/news/?id=saqachfa [Verified]
- Electron features that need a real macOS signature: `safeStorage`, login items, the `cookieEncryption` fuse, and `autoUpdater` (Squirrel.Mac). https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/code-signing.md [Cited]
- `@electron/osx-sign` default entitlements: allow-jit, audio-input, bluetooth, camera, print, usb, location, photos-library. https://raw.githubusercontent.com/electron/osx-sign/main/entitlements/default.darwin.plist [Verified]. Keep `allow-jit` and `com.apple.security.device.audio-input` (mic and line-in are inputs); drop camera, location and photos. System-audio capture on macOS 14.2+ needs the `NSAudioCaptureUsageDescription` Info.plist key. https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.device.audio-input; https://raw.githubusercontent.com/electron/electron/main/docs/api/desktop-capturer.md [Verified correction]
- Windows options (Microsoft, 2026-04-20): Store MSIX free, re-signed by Microsoft, no warnings. Azure Artifact Signing ~$9.99/month for organizations in US/Canada/EU/UK and individuals in US/Canada only; no hardware token, CI integration, validation in a few business days. OV $150–300/year worldwide, keys on HSM or token since June 2023. EV $400+/year, "same as OV since 2024". Self-signed blocks public users; unsigned gets a "strong SmartScreen block". https://raw.githubusercontent.com/MicrosoftDocs/windows-dev-docs/docs/hub/apps/package-and-deploy/code-signing-options.md [Verified]
- SmartScreen: signed apps show "unrecognized" until reputation builds ("several weeks and hundreds of clean installs"); reputation carries only under the same signing identity; Windows 11 Smart App Control blocks unsigned files without reputation. https://raw.githubusercontent.com/MicrosoftDocs/windows-dev-docs/docs/hub/apps/package-and-deploy/smartscreen-reputation.md [Verified]
- Electron's code-signing page says EV is required and that Artifact Signing removes SmartScreen warnings; Microsoft's 2026 docs contradict both. Follow Microsoft. [Verified correction]
- Artifact Signing tiers, billing rules and the January 2026 GA date come from third parties only. [Unverified]
- `jsign` can sign Windows builds with Artifact Signing from Linux or macOS CI. Electron code-signing doc. [Cited]
- Budget $99/year and notarize every macOS build in CI; the Windows route depends on developer location (Artifact Signing ~$120/year if eligible, otherwise OV or the Store). [Inference] Whether Steam builds need notarization or signing is unknown.

## Steam
- steamworks.js: last npm release 0.4.0 (2024-08-06). Native module, main process only; don't copy its README's `contextIsolation: false` example. Prebuilt binaries exist only for win32-x64, linux-x64 and darwin x64/arm64 (it throws on Windows and Linux arm64). `electronEnableSteamOverlay()` forces `in-process-gpu`, `disable-direct-composition` and a 60 Hz repaint. https://registry.npmjs.org/steamworks.js; https://raw.githubusercontent.com/ceifa/steamworks.js/main/index.js; https://raw.githubusercontent.com/ceifa/steamworks.js/HEAD/README.md [Verified]
- Overlay issue #102 is still open: it works on Windows if Steam initializes before `app.whenReady()`, is broken on macOS, and one user got it working only on Linux under Proton. https://github.com/ceifa/steamworks.js/issues/102 [Verified]
- `in-process-gpu` drops GPU-process isolation, so a driver crash could take down the app: make the overlay an optional Steam-only switch, test it with WebGPU per OS, keep Steamworks behind narrow IPC. AMD SteamOS devices need forced WebGPU or WebGL2; Steam Deck scope is a product call (hardware-tiers notes: out of scope). [Inference]
- Unknown: Steam Input's effect on the Gamepad API and WebHID, the overlay with WebGPU backends, Deck Verified rules and Steam Linux Runtime behavior.

## CI and GPU testing
- Runner labels: `windows-2025`, `windows-11-arm`, `macos-26` (arm64), `macos-26-intel`, `macos-15-intel`, `ubuntu-22.04`, `ubuntu-24.04`, `ubuntu-26.04` and `-arm` variants. https://raw.githubusercontent.com/actions/runner-images/main/README.md [Verified]
- Container measurement [Measured]: adapter vendor "google", architecture "swiftshader", `isFallbackAdapter` true, description empty. Compute, offscreen rendering and `copyTextureToBuffer` readback work. `configure()` accepts `rgba16float` with extended tone mapping. Presenting the canvas fails headless and headed under Xvfb with every flag set tried: pending promises reject with "A valid external Instance reference no longer exists." No `shader-f16`; subgroup size 4. A 32-byte-per-particle compute step plus a 1-pixel additive point draw took ~22 ms for 20k and ~131 ms for 300k particles (software timing, not GPU data).
- CPU adapters are blocklisted (`CPUAdapter`) unless `--enable-unsafe-webgpu` is set; that flag alone gave the SwiftShader adapter. https://raw.githubusercontent.com/chromium/chromium/main/gpu/config/webgpu_blocklist_impl.cc [Verified]
- Electron's `GPUFeatureStatus` has no WebGPU field; `--ozone-platform=headless` must be passed on the command line. https://raw.githubusercontent.com/electron/electron/main/docs/api/structures/gpu-feature-status.md; https://raw.githubusercontent.com/electron/electron/main/docs/api/command-line-switches.md [Verified]
- Test plan [Inference]. Tier 1, hosted runners, every push: WGSL compile, compute passes read back against CPU references, render-to-texture against SwiftShader goldens with tolerances, a few thousand particles, no canvas screenshots as oracle. Tier 2, real GPUs before release (Windows discrete GPU, Apple-silicon Mac, Linux AMD box): presentation, frame pacing, fullscreen and multi-monitor, HDR output, performance, Steam overlay, physical pads, WebHID. Log adapter info in every GPU job; fail hardware jobs on a fallback adapter (check `isFallbackAdapter` or architecture, as description is empty). An end-to-end test checks that broken presentation falls back to WebGL2.
- Fallback detection: when presentation is broken, `configure()` still succeeds and offscreen readback still works, so neither detects it. [Verified correction: measured in this container] Present a few frames at startup with a WebGPU promise pending and treat a rejection, a `getCurrentTexture()` error or `device.lost` within a timeout as failure. The message is Dawn's wire-client text for callbacks cancelled when the GPU connection shuts down, so `device.lost` likely fires too (inference from source, not measured). https://raw.githubusercontent.com/google/dawn/main/src/dawn/wire/client/Client.cpp; https://raw.githubusercontent.com/chromium/chromium/156.0.8078.96/third_party/blink/renderer/modules/webgpu/gpu_device.cc
- Unverified: hosted runners behaving like this container, reproduction on Electron 45, Windows and macOS hosted-runner adapters, Electron offscreen capture of a WebGPU canvas, cache paths.
