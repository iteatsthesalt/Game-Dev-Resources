## claude-browser
- [verified] The latest @anthropic-ai/sdk on npm is 1.8.0 (dist-tag latest), published 2026-11-10. It is moving fast: 1.0.0 came out 2026-10-21, and eight minor releases followed in three weeks.
  => Pin an exact SDK version in package.json and the lockfile, never a range. Rebuild the vendored bundle on purpose. A version at least two weeks old (1.3.0 or later is fine) avoids day-old releases.
- [verified] The SDK refuses to start in a browser-like environment (window plus window.document plus navigator present) unless you pass `dangerouslyAllowBrowser: true`.
  => The shared core must always build the client as `new Anthropic({ apiKey, dangerouslyAllowBrowser: true })`.
- [verified] The SDK sends the header `anthropic-dangerous-direct-browser-access: true` only when the dangerouslyAllowBrowser option is set, not merely because it runs in a browser. In an MV3 service worker (no window), the SDK does not throw, but it also sends no header unless you set the option.
  => Set the option in every context: PWA page, extension popup or side panel, extension service worker, and Android WebView. Otherwise the CORS headers are missing (see the CORS facts below).
- [verified] SDK 1.x sends `anthropic-version: 2026-10-21` and sends the API key as `Authorization: Bearer <key>`, not `x-api-key`. It also adds x-stainless-* headers (os, arch, lang, runtime, retry-count, timeout and others).
  => Any raw-fetch fallback should match these headers. Debugging docs should mention that the key travels in the Authorization header.
- [verified] On API version 2026-10-21, every Messages request that sends temperature, top_p or top_k returns a 400.
  => Never send sampling parameters. Fate and randomness come from client-side seeded RNG, not from model temperature.
- [verified] SDK 1.8.0 package layout: type commonjs; dual exports (import maps to .mjs, require maps to .js); a `browser` field that swaps ./internal/node.* for stubs that throw on use; sideEffects false. Dependencies are @opentelemetry/api, standardwebhooks and json-schema-to-ts; zod is a peer dependency.
  => Bundlers that honour the browser field (esbuild with --platform=browser) produce a browser-safe build. zod does not need to be installed for the core client.
- [verified] esbuild 0.28.2 (published 2026-08-08) bundles the SDK into one self-contained browser file. IIFE minified: 376,100 bytes (gzip -9: 83,224). ESM minified: 376,168 bytes (gzip: 83,253). Unminified ESM: 1,046,977 bytes. The output has no require() calls, no dynamic import(), and no eval or new Function.
  => Vendor one pinned file, e.g. lib/anthropic.iife.js, about 83 KB over the wire. It works as a classic script in the PWA, as a local script in the MV3 extension (no remote code, and no unsafe-eval needed under the MV3 CSP), and as an asset in the WebView. Build it in GitHub Actions or commit it with its version in the filename. A thin raw-fetch adapter would be about 5-10 KB if size matters more than SDK helpers.
- [verified] The bundled SDK runs in a bare context with no `process` and no `require`, using only web globals. messages.create, messages.stream (text events plus finalMessage) and models.list (auto-paginating) all work against a stub fetch.
  => Streaming (needed for reading finds aloud as they arrive) works with the browser fetch ReadableStream. No Node polyfills are needed.
- [verified] api.anthropic.com answers CORS preflights from any origin. I tested https://iteatsthesalt.github.io, chrome-extension://..., moz-extension://..., https://appassets.androidplatform.net and Origin: null. Every one got HTTP 200 with access-control-allow-origin: *, the requested headers echoed back in access-control-allow-headers, methods DELETE, GET, HEAD, OPTIONS, PATCH, POST, PUT, and max-age 600.
  => One shared fetch path works unchanged in the PWA, the Chrome/Edge/Firefox extension, and an Android WebView served through WebViewAssetLoader (https://appassets.androidplatform.net), even from a file:// page (origin null). No proxy and no Kotlin network bridge are needed.
- [verified] Real (non-preflight) responses carry access-control-allow-origin: * and access-control-expose-headers: * only when the request includes `anthropic-dangerous-direct-browser-access: true`. Without that header there is no ACAO, so a browser cannot read the response, error bodies included. `Vary` lists that header.
  => Without the header even a bad-key error looks like an opaque network or CORS failure. With it, the app can read error JSON (401 invalid key, 400, 429) and rate-limit headers such as retry-after, because expose-headers is *.
- [likely] Allow-origin is the wildcard * (the origin is not reflected), so credentialed requests (fetch with credentials:'include') would be blocked by the browser.
  => Never set credentials:'include' on API calls. The key travels only in a header.
- [likely] The API treats an `Authorization: Bearer sk-ant-...` API key as an API key, the way the SDK 1.x sends it.
  => Raw-fetch fallbacks may use either x-api-key or Bearer. Stay with what the SDK sends.
- [verified] GET /v1/models lists the models available to the key, newest first. Query: after_id, before_id, limit (default 20, max 1000), lifecycle[] (active/deprecated/retired; the default is active plus deprecated). Each item has type, id, display_name, created_at, deprecated_at, retires_at, lifecycle, line (haiku/sonnet/opus/fable/mythos), max_input_tokens, max_tokens, and capabilities. capabilities contains batch, citations, code_execution, context_management, effort.{low,medium,high,xhigh,max}, image_input, pdf_input, server_tools.{web_search,code_execution}, structured_outputs, and thinking.types, each with a supported flag. The page has first_id, last_id and has_more. There is no price field.
  => Fill the model picker with one GET /v1/models?limit=1000. Filter to lifecycle=='active' and capabilities.server_tools.web_search.supported for AI Search, and use display_name. Ship a static price table keyed by model id with an 'unknown price' fallback, plus a hard-coded fallback list (claude-opus-5-5, claude-sonnet-5-5, claude-haiku-5-5) for when the call fails. Validating the key with this call costs no tokens.
- [verified] Web search costs $10 per 1,000 searches ($0.01 each) plus normal token costs. Search results count as input tokens, both in later search iterations within the same turn and in later turns. Each search counts once however many results it returns, and a search that fails with an error is not billed. Usage reports the count in usage.server_tool_use.web_search_requests.
  => Show the cost per AI Search computed from usage: web_search_requests × $0.01 plus tokens × price. Cap max_uses (for example 3 per model, and fewer per role in AI-team mode).
- [verified] Token costs that apply to one AI Search: the tool-use system prompt adds 286 input tokens with tool_choice auto on Opus 5.5, Sonnet 5.5 and Haiku 5.5. Prices per million tokens (input/output): Opus 5.5 $4/$20, Sonnet 5.5 $2/$10, Haiku 5.5 $0.10/$0.50 for prompts up to 100K tokens ($0.50/$2.50 above that). Cache hits cost $0.20, $0.10 and $0.01. Code execution is free when web_search_20260209 or later is in the request.
  => The client-side cost estimator can use these constants. Keep Haiku 5.5 prompts under 100K tokens to avoid the higher tier.
- [likely] Estimated cost of one AI Search with 3 searches, assuming 5-20K result tokens per search and 20-70K total input across the server loop (dynamic filtering lowers this), plus 2-4K output. Haiku 5.5: about $0.035-0.04. Sonnet 5.5: about $0.09-0.21. Opus 5.5: about $0.15-0.39. An AI team of those three models at 3 searches each: about $0.27-0.64. The search fee alone is $0.03 per model.
  => Default AI Search to Sonnet 5.5 or Haiku 5.5 with max_uses 3. Make AI-team mode opt-in, or cap it by an estimated budget. Show the running dollar total.
- [unverified] Structured outputs (output_config.format) are documented as incompatible with citations: 'The API returns a 400 error if citations are enabled with output_config.format.' The web search doc says 'Citations are always enabled for web search.' No official page says whether web_search plus output_config.format returns a 400.
  => Do not rely on output_config.format together with web_search. Use the safe pattern: a client tool `report_finds` with strict:true, additionalProperties:false and required fields (url, title, why, tags, etc.), with tool_choice {type:'auto'}, and a system prompt saying to call report_finds exactly once, alone, after all searches. Verify that it was called, and if not, retry once with a nudge.
- [verified] If Claude calls web_search and a client tool (for example report_finds) in the same parallel group, the API returns stop_reason 'tool_use' and does not run the search yet. To continue, send a user message containing only tool_result blocks, one per client tool_use, and keep the same tools array.
  => In the agent loop: when report_finds arrives with no pending server_tool_use, accept its input as final. If a search is still pending, return a tool_result for report_finds ('received, finish searching then call again') and continue, with a cap on the number of rounds.
- [verified] Handling pause_turn: send the paused assistant content back unchanged with the same tools. If the response includes a `container` (dynamic filtering runs code execution), send its ID back too, or files from earlier in the turn are lost. Keep every paused response in messages, in order. A turn can pause again, so cap continuations.
  => The core's runSearch() loop must store response.container?.id and pass `container` on continuation requests, with a maximum of about 5 continuations.
- [verified] On web_search_20260209 and later, allowed_callers defaults to ['code_execution_20260120'] (dynamic filtering). Models that do not support programmatic tool calling need allowed_callers:['direct'], or the request returns a 400 that says to set it. The Models API exposes this as capabilities.code_execution.supported. Haiku 5.5 is listed as supporting programmatic tool calling.
  => When building the web_search tool for a chosen model, set allowed_callers:['direct'] when capabilities.code_execution.supported is false, so the model picker never produces a 400.
- [verified] A newer tool version, web_search_20260318, adds `response_inclusion` ('full' by default, or 'excluded'). 'excluded' drops nested search blocks that a completed code-execution call already consumed, so the response is smaller while token usage stays the same. SDK 1.8.0 types include both web_search_20260209 and web_search_20260318.
  => Keep response_inclusion 'full' (or use 20260209) so the app can check that every URL in report_finds appears in a web_search_result, and drop hallucinated links. Consider 'excluded' only if response size becomes a problem on mobile.
- [verified] An org admin can disable web search in the Claude Console. A request that includes the tool then fails with a 400 invalid_request_error saying web search is not enabled, not with an error code inside the search result.
  => Map this 400 to a friendly message ('Enable web search in your Claude Console settings') and fall back to non-search Tuned or Fate modes.
- [verified] Web search answers carry citations, and the docs say that when API output is shown to end users, citations to the original source must be included.
  => Every AI-found card must show and link its source URL and title (the report_finds schema needs url and source_title). Read-aloud mode should name the source.
RISKS:
- Whether web_search combined with output_config.format returns a 400 is unverified: there was no real key to test and no official statement. The spec should use the strict report_finds client tool instead.
- CORS headers were observed only on 401 responses (dummy key). Success (200) and streaming (SSE) responses are expected to carry the same access-control-allow-origin: * but were not seen live.
- Direct browser access is an opt-in Anthropic could change or restrict, for example by org policy. No official docs page describing the header was found, only the SDK source and community posts.
- BYOK key exposure: anything that runs script in the PWA origin, extension page or WebView can read the stored key. Find titles and snippets are untrusted web text, so any XSS from them could exfiltrate the key.
- The cost estimate rests on assumed tokens per search (5-20K). Real search-result sizes and dynamic-filtering savings vary, so AI-team mode could cost several times the estimate.
- SDK release churn (1.0.0 to 1.8.0 in three weeks) plus a 367 KB minified bundle (83 KB gzip) that also carries Managed Agents and Admin resources and OpenTelemetry. Class-method code cannot be tree-shaken.
- Haiku 5.5 support for dynamic filtering (web_search_20260209 with the default allowed_callers) is inferred from Anthropic's reference, not tested live.
- Mixed server-plus-client tool turns (report_finds called alongside a pending web_search) need careful loop logic. A naive loop could stop before searches run, or loop forever without a continuation cap.
