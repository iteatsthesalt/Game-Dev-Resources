## platform-shells
- [verified] MV3 bans remotely hosted code. All extension logic must be in the package: no JS from a developer server, no library from a CDN (jsDelivr included), and no bundled third-party library that fetches remote code at runtime. JS, Wasm and CSS should be bundled. Remote data such as a JSON config or API responses is allowed.
  => Vendor every library into the extension build: the shared core, js-dos, EmulatorJS, v86 and any UI libs, plus their .wasm and core files. Configure EmulatorJS (EJS_pathtodata) and js-dos to load their cores and wasm from extension-relative paths, never from their default CDNs. The PWA may use a CDN, but the extension build must copy from a local vendor/ folder, so it is simpler to vendor for all three shells.
- [verified] The default MV3 extension_pages CSP is "script-src 'self';". It does not include 'wasm-unsafe-eval'. The minimum allowed CSP is "script-src 'self' 'wasm-unsafe-eval' 'inline-speculation-rules'; object-src 'self';" and cannot be relaxed further: no remote script hosts and no 'unsafe-eval'.
  => Set manifest content_security_policy.extension_pages to "script-src 'self' 'wasm-unsafe-eval'; object-src 'self';". Without it, WebAssembly is blocked and none of the emulators (js-dos, EmulatorJS, v86) will run. Use no inline scripts and no eval or new Function in the shared core.
- [verified] Sandboxed extension pages may use eval/new Function and remotely hosted code, but they get no chrome.* APIs.
  => If any emulator build turns out to need eval, host it in a manifest 'sandbox' page that talks to the main page over postMessage. Keep everything else on normal extension pages.
- [likely] The MV3 default and minimum CSPs have no frame-src or default-src directive, so extension pages, including the side panel, may iframe https sites. The embedded site's own X-Frame-Options or frame-ancestors still decides whether it renders.
  => The archive.org /embed/ player can sit in an iframe on an extension page or in the side panel. A general Stumble find must not depend on iframes, because many sites forbid framing. Open finds in the real tab instead.
- [likely] Cookie and storage partitioning: if a chrome-extension:// page iframes a site the extension has host permissions for, that site gets its top-level storage partition. Third-party cookies are never blocked in subframes when the tab's top-level page is chrome-extension://.
  => Add https://archive.org/* (and its embed/CDN hosts) to host_permissions so the Archive player keeps normal storage inside the extension iframe.
- [verified] chrome.sidePanel needs the 'sidePanel' permission and side_panel.default_path in the manifest. It is in Chrome and Edge from 114. sidePanel.setPanelBehavior({openPanelOnActionClick:true}) makes the toolbar icon open the panel. sidePanel.open() (Chrome 116+) needs a user gesture, such as an action click, a context menu, or a click on an extension page or content script. Firefox has none of this.
  => Use the toolbar action click for Stumble, which navigates the current tab, and do not set openPanelOnActionClick, because it would take over the click. Open the side panel (the feed, Rabbit Hole and voice) from a context-menu item, a keyboard command, or a button on an extension page via sidePanel.open({windowId}).
- [verified] chrome.tabs.update({url}) needs no permission. 'tabs', 'activeTab' or host permissions are needed only to read a tab's url, title or favIconUrl, or to inject scripts.
  => For the Stumble button, call chrome.tabs.update(tab.id,{url}) in action.onClicked, using the tab object passed to the handler. Add 'activeTab' only if Rabbit Hole needs the current page's URL or title, which avoids the broad 'tabs' warning.
- [verified] Keyboard commands: an extension can suggest at most 4 shortcuts (users can add more at chrome://extensions/shortcuts). Each must include Ctrl or Alt. _execute_action is reserved and does not fire commands.onCommand. Global commands are limited to Ctrl+Shift+[0-9]. Firefox also supports _execute_action and _execute_sidebar_action.
  => Suggest 4 shortcuts at most: _execute_action (Stumble, e.g. Alt+Shift+S), open panel or sidebar, next/advance, and toggle listening. Map the panel shortcut to _execute_sidebar_action on Firefox.
- [verified] Requests from an extension service worker or extension page (popup, side panel, tab) to hosts covered by host_permissions bypass CORS. Content scripts stay bound by the page's same-origin policy and CORS.
  => Make AI provider calls from extension pages or the service worker, never from content scripts. List known provider API hosts in host_permissions, and put custom or BYO endpoints (e.g. local Ollama) in optional_host_permissions, requested with permissions.request() from a user click.
- [verified] Popups, side panels and offscreen documents cannot show the microphone permission prompt. The supported pattern is to open a normal extension page in a tab once to call getUserMedia({audio:true}). The grant belongs to the chrome-extension://<id> origin, and other extension contexts can then use the mic.
  => Ship a permission.html 'Enable hands-free' page. On first install, or when SpeechRecognition reports 'not-allowed', open it with chrome.tabs.create; it grants the mic and closes itself. After that, the side panel and full-tab app can start voice.
- [likely] After the one-time grant on the extension origin, webkitSpeechRecognition works in the Chrome side panel and full-tab extension pages.
  => Feature-detect, and treat voice in the extension as best effort. If it fails, fall back to a full-tab Byways page, which behaves like the PWA.
- [verified] Firefox does not support background.service_worker. Since Chrome 121 and Firefox 121, a single manifest may list both background.scripts and background.service_worker: Chrome ignores scripts and Firefox ignores service_worker.
  => Write one ES-module-free background.js that runs as a Chrome service worker and as a Firefox event page. Do not use DOM APIs in it, and do not keep state in globals (persist it with storage.local).
- [verified] Firefox MV3 requires browser_specific_settings.gecko.id for signing (AMO or self-distribution); AMO does not assign one. gecko.data_collection_permissions is required for new AMO submissions from 2025-11-03, is supported from Firefox 140, and the MDN example uses strict_min_version 140.0 with required:['none'].
  => The Firefox manifest needs a fixed id such as 'byways@<owner>', data_collection_permissions {required:['none']}, which is true because everything stays on the device and only user-initiated calls to providers are made, and strict_min_version '140.0'.
- [verified] Chrome's sidePanel API and Firefox's sidebar_action/sidebarAction are incompatible. Firefox's sidebarAction.open() may only be called from a user-action handler.
  => Generate two manifests from one template: Chrome/Edge get side_panel and the 'sidePanel' permission; Firefox gets sidebar_action.default_panel pointing at the same panel.html. Wrap panel opening in a small adapter in the extension shell.
- [verified] Since Chrome 148, Chrome also exposes the promise-based browser.* namespace, so the namespace is no longer a Chrome/Firefox incompatibility.
  => In shell code use const ext = globalThis.browser ?? globalThis.chrome. No webextension-polyfill is needed.
- [likely] Firefox MV3 host permissions are shown at install since Firefox 127, but the user can revoke them at any time, and permissions added in an update are not prompted.
  => On startup and in runtime.onInstalled, check permissions.contains for provider and Archive hosts. Show an onboarding 'Grant access' button that calls permissions.request.
- [verified] Release Firefox installs only signed add-ons. web-ext can sign unlisted (self-distributed) builds through AMO with an API key and secret.
  => CI zips dist/chrome (also used for Edge) and dist/firefox. Optionally run `npx web-ext sign --channel=unlisted` with AMO_API_KEY and AMO_API_SECRET repository secrets, which the user can supply, to produce an installable .xpi. Chrome/Edge friends use 'Load unpacked' or a store listing.
- [likely] Firefox is adding unprefixed SpeechRecognition: BCD lists version_added 160, and Firefox 160 was 'beta' in BCD 8.1.8 with release date 2026-11-10. Firefox now releases about every 2 weeks.
  => Do not assume voice input is missing on Firefox; feature-detect at runtime. Behaviour inside Firefox extension pages is untested, so keep the typed and tap controls fully usable.
- [likely] androidx.webkit: the latest stable is 1.18.0 (2026-10-21). The androidx source tree is already at 1.19.0-alpha02. 1.17.0 added WebViewCompat.navigate, and 1.16.0 made navigation listeners stable.
  => Pin androidx.webkit:webkit:1.18.0. If Gradle cannot resolve it, fall back to the newest 1.17.x. Use only long-stable APIs: WebViewAssetLoader, addWebMessageListener, WebViewFeature.
- [verified] WebViewAssetLoader.DEFAULT_DOMAIN is appassets.androidplatform.net. AssetsPathHandler serves APK assets, and the loader is called from WebViewClient(Compat).shouldInterceptRequest. MIME types: .wasm is application/wasm, .js/.mjs JavaScript, .json application/json, and unknown extensions text/plain. setDomain and setHttpAllowed exist.
  => Bundle the built web core under app/src/main/assets/www and load https://appassets.androidplatform.net/assets/www/index.html. The page gets a secure https origin, so WebAssembly.instantiateStreaming works. Keep the file:// access settings off.
- [verified] Android WebView exposes the Web Speech Recognition API but disables Speech Synthesis.
  => Reading finds aloud in the Android app needs a native TextToSpeech bridge, because window.speechSynthesis is absent. Voice commands may use in-page webkitSpeechRecognition, with a native SpeechRecognizer bridge as fallback.
- [verified] In WebView, recognition uses Chromium's SpeechRecognitionImpl. It calls SpeechRecognizer.isRecognitionAvailable and PackageManager.queryIntentServices(RecognitionService.SERVICE_INTERFACE), and only accepts a Google-provided service (com.google.android.googlequicksearchbox or com.google.android.tts). On Android 11+, the app must declare <queries><intent><action android:name="android.speech.RecognitionService"/></intent></queries> or the lookup returns nothing. TTS likewise needs a query for android.intent.action.TTS_SERVICE.
  => The AndroidManifest needs RECORD_AUDIO, INTERNET, and <queries> for RecognitionService and TTS_SERVICE. On devices without Google speech, the in-page API fails silently, so the native bridge (android.speech.SpeechRecognizer with any provider, or createOnDeviceSpeechRecognizer where available) is the dependable path. Prefer the bridge whenever window.BywaysNative exists.
- [likely] WebView's speech recognition delegate asks for user permission (check_permission=true). The request reaches the app as WebChromeClient.onPermissionRequest with RESOURCE_AUDIO_CAPTURE, and the app must also hold the RECORD_AUDIO runtime permission. Android docs warn against grant(getResources()).
  => In onPermissionRequest, grant only RESOURCE_AUDIO_CAPTURE and only for origin https://appassets.androidplatform.net. If RECORD_AUDIO is missing, request it with ActivityResultContracts.RequestPermission and then grant or deny the pending request. Because hands-free is on by default, ask at first launch with an explanation screen.
- [verified] WebViewCompat.addWebMessageListener injects the JS object only into frames whose origin matches allowedOriginRules, and it is available from the start of page load. addJavascriptInterface exposes its object to every frame.
  => Use addWebMessageListener(webView, "BywaysNative", setOf("https://appassets.androidplatform.net"), …) for all native bridges: speech, TTS, share, fetch, file save. Do not use addJavascriptInterface, so third-party iframes such as archive.org embeds can never reach the bridge. Check WebViewFeature.WEB_MESSAGE_LISTENER at startup.
- [likely] Native fetch bridge for CORS: WebView's shouldInterceptRequest cannot see POST bodies, so CORS-free AI calls need a message bridge to native HTTP. JS posts {id,url,method,headers,body}, Kotlin performs the request (HttpURLConnection or OkHttp), and replies through JavaScriptReplyProxy.postMessage. Streaming arrives as several messages.
  => The shared core gets a transport interface (browserFetch / extensionFetch / nativeFetch) chosen per shell. The Android bridge should only allow https URLs. API keys stay in the web layer's storage and are passed per request, never logged.
- [verified] WebView defaults: JavaScript disabled, DOM storage disabled, mediaPlaybackRequiresUserGesture=true. Third-party cookies are blocked by default for apps targeting Lollipop or later; setAcceptThirdPartyCookies is per-WebView.
  => Set javaScriptEnabled=true, domStorageEnabled=true, mediaPlaybackRequiresUserGesture=false (needed for lean-back auto-advance audio and TTS-paced playback), and CookieManager.setAcceptThirdPartyCookies(webView,true) so the archive.org embed iframe behaves like a browser. Leave allowFileAccess and allowContentAccess off.
- [verified] Fullscreen in WebView works only if WebChromeClient.onShowCustomView is overridden; otherwise WebView tells the page fullscreen is unsupported. onHideCustomView must remove the view.
  => Implement onShowCustomView/onHideCustomView by adding the view to a full-screen FrameLayout, hiding system bars with WindowInsetsControllerCompat, and handling Back. The emulator canvases and Archive embeds need this; iframes also need allow="fullscreen".
- [verified] File pickers: WebChromeClient.onShowFileChooser with FileChooserParams.createIntent() and FileChooserParams.parseResult() delivers content:// files to <input type=file>.
  => The Emulator Lab uses a plain <input type=file> in all shells. Android implements onShowFileChooser with registerForActivityResult, calls onReceiveValue(null) on cancel or a stale callback, and allows multiple files and */* (ROM, ISO and IMG types are not standard MIME types).
- [verified] navigator.share is not available in Android WebView.
  => For share-by-link on Android, use a native bridge that calls Intent.createChooser(ACTION_SEND text/plain). Add an ACTION_SEND text/plain intent-filter so a shared URL becomes a 'Save to collection' or 'Rabbit Hole from this' entry. Add an https or custom-scheme VIEW filter for Byways share links.
- [verified] For apps targeting API 36 on Android 16, predictive back is on by default: Activity.onBackPressed is not called and KEYCODE_BACK is not dispatched. OnBackPressedCallback still works, and android:enableOnBackInvokedCallback=false is a temporary opt-out. Edge-to-edge is enforced and the windowOptOutEdgeToEdgeEnforcement opt-out is disabled.
  => Use an OnBackPressedDispatcher callback whose isEnabled tracks custom view showing || webView.canGoBack() || the SPA's own history (ask the web layer through the bridge). Pad the WebView with system-bar and IME insets via ViewCompat.setOnApplyWindowInsetsListener.
- [likely] Service worker requests inside WebView do not pass through WebViewClient.shouldInterceptRequest. They need ServiceWorkerControllerCompat / ServiceWorkerClientCompat.
  => The Android shell should skip registering the PWA service worker, because its assets are already local. Skip it when window.BywaysNative exists, or route ServiceWorkerClientCompat.shouldInterceptRequest to the same asset loader.
