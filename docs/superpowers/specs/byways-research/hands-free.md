## hands-free
- [verified] SpeechRecognition support as of BCD 8.1.8 (data 2026-11-02): Chrome desktop 139 unprefixed (webkit prefix from 33); Chrome Android 139 (webkit 33); Edge 139 (webkit 79); Safari macOS 14.1 and iOS 14.5 webkit prefix only; Samsung Internet 30.0 unprefixed (webkit 2.0); Firefox desktop 160 unprefixed only; Firefox Android not supported.
  => Feature-detect with `window.SpeechRecognition || window.webkitSpeechRecognition`, never by user-agent. On Firefox Android and any browser without it, hands-free falls back to read-aloud, auto-advance, headset buttons and keyboard, with no voice commands.
- [likely] Firefox desktop 160 turns SpeechRecognition on by default. In BCD 8.0.0 (May 2026) it sat behind the media.webspeech.recognition.enable pref from Firefox 142. BCD dates the 160 release 2026-11-10 and still marked it beta in its 2026-11-02 snapshot.
  => Treat Firefox desktop as newly supported, test it on real hardware, and keep the voice layer engine-agnostic. It is too new to rely on. Whether Firefox recognises on-device or in the cloud is unknown.
- [likely] Chrome's default recognition is server-based: audio is sent to Google, and it does not work offline. Safari uses Siri (Siri must be enabled). Edge uses an Azure speech component and does not work on Edge for Mac ARM.
  => Default cloud recognition breaks the 'everything stays on the device' promise, especially for always-on listening. The spec should try on-device first. Cloud recognition should run only after an explicit one-time opt-in that names the vendor ('your voice goes to Google/Apple/Microsoft'). When offline without on-device support, voice commands are disabled with a clear message.
- [verified] The on-device API exists: the `processLocally` attribute, static `SpeechRecognition.available({langs, processLocally})` resolving to 'unavailable' | 'downloadable' | 'downloading' | 'available', and static `install({langs, processLocally})` returning Promise<boolean>. It ships in Chrome/Edge desktop 139 and Firefox 160. It is NOT in Chrome Android, Safari, Samsung Internet or WebView. The `quality` option ('command' | 'dictation' | 'conversation', default 'command') is experimental in Chrome 150 only.
  => On desktop Chromium and Firefox, call available({langs:[lang], processLocally:true}) at startup. If it returns 'downloadable', show a 'Download offline voice pack' button that calls install() from a click. Then run with processLocally=true and quality:'command' where supported.
- [verified] Contextual biasing exists: `recognition.phrases` takes SpeechRecognitionPhrase(phrase, boost) objects, in Chrome 142+ and Firefox 160 (desktop only). The error enum includes 'phrases-not-supported'.
  => Bias the recogniser toward the command words and app terms ('Byways', 'stumble', 'rabbit hole', 'fate'). If 'phrases-not-supported' fires, retry without phrases.
- [verified] `start(MediaStreamTrack)` exists (Chrome 135+ and Firefox 160, desktop only), so the app can feed recognition its own getUserMedia track.
  => An optional path: pass a getUserMedia({audio:{echoCancellation:true}}) track to reduce the app's own read-aloud triggering commands. Whether echo cancellation actually removes speechSynthesis output is unverified, so test it before relying on it.
- [verified] `continuous` works in Chrome desktop 33+, Edge 79+, Firefox 160 and Safari 17+ (before 17 it was partial and returned multiple results even when false). On Chrome Android, Samsung Internet and Android WebView, 'The property can be set, but has no effect.'
  => The voice engine needs an auto-restart loop for every platform. On Android browsers each utterance ends the session, so the loop restarts after every phrase.
- [likely] On Chrome for Android, each microphone start plays an OS beep. With continuous listening the mic restarts constantly, which is noisy and frustrating. Native Android SpeechRecognizer beeps on start and stop by hard-coded behaviour.
  => In the Android-browser PWA, do not default to always-on listening. Default to tap-to-talk (or headset button) plus read-aloud and auto-advance, and recommend the Android app for true hands-free. The Android app uses native continuous mode (see the native facts).
- [verified] The recognition error codes are: no-speech, aborted, audio-capture, network, not-allowed, service-not-allowed, language-not-supported, phrases-not-supported.
  => Restart policy: restart immediately on 'end', 'no-speech' and 'aborted' when the app did not abort. Restart with exponential backoff (1s to 30s, then give up and show a message) on 'network'. Stop and show guidance without retrying on 'not-allowed', 'service-not-allowed', 'audio-capture' and 'language-not-supported'.
- [unverified] How long a Chrome or Safari session lasts before ending on its own (silence timeouts, maximum session length) is not documented in anything checked.
  => Do not hard-code timeouts. Restart on every 'end' event, cap restarts (for example at most 10 per minute), and add an app-level idle timeout (for example stop listening after 10 minutes with no recognised command, announced aloud).
- [verified] SpeechRecognition is [SecureContext, Exposed=Window], and speechSynthesis is a property of Window. Neither exists in workers or service workers.
  => The MV3 extension service worker cannot listen or speak with these APIs. Voice must run in a document (side panel, popup, Byways tab or offscreen document), or use chrome.tts from the worker. GitHub Pages and WebViewAssetLoader origins are HTTPS, so they are fine.
- [likely] Chrome blocks speechSynthesis.speak() until the page has had a user activation (a change made around Chrome 71). The spec has a 'not-allowed' synthesis error for this.
  => 'Hands-free on by default' cannot mean zero touches on the web. Each launch shows one large 'Start' control (click, Enter or Space). That one press unlocks speech, asks for the mic if needed, starts listening and starts lean-back. The Android app's native TTS has no such limit and can start fully hands-free.
- [unverified] Whether SpeechRecognition.start() needs a user gesture differs by browser and could not be confirmed. Microphone permission is granted per origin.
  => Always make the first start() call from the same 'Start' press that unlocks speech. Before prompting, check navigator.permissions.query({name:'microphone'}) where supported (Chrome 64, Firefox 132, Safari 16; not WebView) and show a one-line explainer.
- [likely] GitHub Pages serves every project page of an account from one origin (iteatsthesalt.github.io), so a microphone grant to Byways also applies to any other page under that account.
  => State this in the privacy notes. Do not host untrusted pages on the same account's Pages origin; a custom domain would isolate Byways.
- [verified] SpeechSynthesis is supported in Chrome 33, Chrome Android 33, Edge 14, Firefox 49, Firefox Android 62, Safari 7, iOS 7 and Samsung Internet 3.0, but NOT in Android WebView.
  => The Android wrapper must bridge native android.speech.tts.TextToSpeech to the shared JS core behind one speak/cancel/voices interface. The core picks the web or native backend at runtime.
- [verified] Synthesis quirks: on Android browsers pause() behaves the same as cancel(); Chrome's `boundary` event does not fire as expected (crbug 40715888); Firefox voices only start loading after the first getVoices() call; the voiceschanged event exists in Safari only from version 16.
  => Split read-aloud text into one-sentence utterances queued by the app, and implement pause as cancel plus resume from the current sentence index. Do not drive word highlighting from boundary events in Chrome. Load voices with getVoices() at start, then voiceschanged, with a short polling fallback.
- [verified] Voices report whether they need the network: SpeechSynthesisVoice.localService on the web, and Voice.isNetworkConnectionRequired() natively on Android.
  => For privacy and offline use, auto-select a local voice and mark network voices as 'online' in the voice picker.
- [unverified] Chrome's Google network voices are commonly reported to stop long utterances after about 15 seconds.
  => Sentence chunking (above) avoids this anyway. Never queue a whole article as one utterance.
- [unverified] Web SpeechRecognition inside Android WebView: BCD lists webkitSpeechRecognition from 4.4.3 and unprefixed from 139 (continuous has no effect, no processLocally), and react-speech-recognition lists 'Android webview' as supported. In practice it is widely reported as unreliable, and every hybrid framework checked (Capacitor, Cordova, Expo) ships a native SpeechRecognizer plugin instead.
  => The Android app must not depend on the WebView's web API. It injects a native recogniser bridge (on-device when possible), and the shared core prefers the bridge whenever it is present.
- [verified] For a WebView page to use getUserMedia, the app must override WebChromeClient.onPermissionRequest, hold the RECORD_AUDIO (and MODIFY_AUDIO_SETTINGS) runtime permission, and call request.grant() for android.webkit.resource.AUDIO_CAPTURE.
  => The Kotlin wrapper implements onPermissionRequest, limited to the app's own origin, in case any web mic feature (for example a WASM wake word) is used. Otherwise all mic use goes through the native bridge.
- [likely] Native on-device recognition: SpeechRecognizer.isOnDeviceRecognitionAvailable() is used from API 31 (S); createOnDeviceSpeechRecognizer() and triggerModelDownload() are used from API 33 (Android 13). On-device needs a downloaded language model (Settings > Security and privacy > More privacy settings > Android System Intelligence > On-device speech recognition). On Android 13 the download opens a dialog; on 14+ it can complete or be scheduled.
  => In the Android app: if on-device recognition is available, create the on-device recogniser and add EXTRA_PREFER_OFFLINE. If the language is missing, offer 'Download offline voice' (triggerModelDownload). Fall back to the cloud recogniser only with the same opt-in as the web.
- [verified] Native continuous listening: on Android 13+, pass EXTRA_AUDIO_SOURCE (an app-owned AudioRecord pipe) with EXTRA_SEGMENTED_SESSION. Results then arrive through onSegmentResults and the session ends with onEndOfSegmentedSession; this also avoids the start/stop beep. Android 12 and below has no true continuous mode: only silence-length extras (for example 600000 ms) or a restart loop.
  => Set Android 13 (API 33) as the hands-free baseline for the Android app. On API 26-32, fall back to a restart loop (with beeps) or tap-to-talk, and say so in the UI.
- [verified] Native setup requirements: the RECORD_AUDIO runtime permission; a manifest <queries> entry for intent action android.speech.RecognitionService (without it binding fails with 'Bind to system recognition service failed with error 10'); a <queries> entry for android.intent.action.TTS_SERVICE for TextToSpeech; and SpeechRecognizer calls posted to the main thread.
  => Put both <queries> blocks and RECORD_AUDIO into the wrapper's AndroidManifest template. All SpeechRecognizer calls go through a main-thread Handler.
- [verified] Native error codes to handle: ERROR_NO_MATCH, ERROR_SPEECH_TIMEOUT, ERROR_RECOGNIZER_BUSY, ERROR_TOO_MANY_REQUESTS (Android 12+), ERROR_INSUFFICIENT_PERMISSIONS, ERROR_NETWORK / ERROR_NETWORK_TIMEOUT / ERROR_SERVER / ERROR_SERVER_DISCONNECTED, ERROR_LANGUAGE_UNAVAILABLE ('supported, but not yet downloaded'), ERROR_LANGUAGE_NOT_SUPPORTED.
  => Native restart loop: restart at once on NO_MATCH and SPEECH_TIMEOUT; destroy and recreate on RECOGNIZER_BUSY; back off on TOO_MANY_REQUESTS and network errors; stop and prompt on INSUFFICIENT_PERMISSIONS and the language errors. Map these to the same event names as the web engine so the shared core handles both.
- [likely] Android recognisers often return nothing for very short single words until the user says more. Google recommends the 'web_search' language model for this, and on-device recognition handles single words better.
  => Choose commands that are distinct and at least two syllables where possible ('next one', 'go back', 'save it', 'read it'), accept one-word synonyms, and set EXTRA_LANGUAGE_MODEL=web_search plus EXTRA_BIASING_STRINGS (API 33) with the command list.
- [verified] Chrome extensions: the chrome.offscreen.Reason enum includes USER_MEDIA and AUDIO_PLAYBACK but no speech-recognition reason. Offscreen documents can only use chrome.runtime messaging. chrome.tts needs the "tts" permission. Firefox has no sidePanel (Chrome/Edge 114+) and offers sidebarAction instead (Firefox 54+). BCD has no tts or offscreen entries, which suggests they are Chrome-only.
  => Run the extension's hands-free loop in the Chrome side panel or Firefox sidebar, or in a full Byways tab, and only while that surface is open. Never listen browser-wide. Read aloud with speechSynthesis in the page, or chrome.tts from the worker on Chrome.
- [unverified] In an extension popup or offscreen document, SpeechRecognition or getUserMedia is commonly reported to fail with 'not-allowed', because those surfaces cannot show the permission prompt. The common workaround is to open a visible extension page once to grant the mic to the chrome-extension:// origin.
  => Add a one-time 'Enable voice' extension tab that calls getUserMedia to get the grant, then hands control back to the side panel. Test that the side panel itself can prompt before relying on it.
- [likely] Recognition is reported to be absent or broken in Brave desktop (waiting on on-device Web Speech, as of July 2025) and in Chrome on iOS (last tested 2023).
  => Detection must be functional, not just checking that the constructor exists: run a test start. Treat 'network' or 'service-not-allowed' on the first try as 'voice unavailable on this browser' and switch to the non-voice hands-free mode.
- [likely] A speaker's output being picked up by the mic is a known problem when recognition runs alongside audio output.
  => Make the voice loop half-duplex by default: while the app is speaking (plus about 400 ms after), ignore recognition results except an exact 'stop' or 'pause', and also accept those through keyboard, tap or headset.
- [likely] Android limits mic access: background apps cannot use the microphone (Android 9+), the OS shows a mic-in-use indicator (Android 12+), and background capture needs a foreground service of type microphone (Android 14+).
  => The Android app listens only while in the foreground and stops in onPause/onStop, so no foreground service is needed. The web core likewise pauses listening on visibilitychange=hidden and shows its own 'Listening' indicator.
- [verified] Media Session action handlers (headset and lock-screen next, previous, play and pause) are supported in Chrome 73, Chrome Android 57, Firefox 82 (Android has no media UI), Safari 15 and Samsung Internet 7.0, but NOT in Android WebView.
  => Map nexttrack to Stumble next, previoustrack to back, and play/pause to lean-back toggle while read-aloud is active. This gives hands-free control that cannot be triggered by accident. The Android app uses a native MediaSession for the same mapping.
- [verified] Screen Wake Lock is supported in Chrome 84, Chrome Android 84, Firefox 126, Safari 16.4 (iOS home-screen web apps only from 18.4) and WebView 84.
  => In lean-back mode, request navigator.wakeLock.request('screen'), re-acquire it on visibilitychange, and release it on pause or stop.
- [verified] The prefers-reduced-motion media query is supported in Chrome 74, Firefox 63, Safari 10.1, iOS 10.3, Samsung Internet 11 and WebView 74.
  => Auto-advance and Stumble transitions switch to an instant swap or a short fade when reduced motion is set, plus an in-app 'Reduce motion' toggle that overrides the OS.
- [verified] On-device wake-word and keyword options: @picovoice/porcupine-web 4.0.1 (Apache-2.0) runs offline in WASM but 'requires a valid Picovoice AccessKey at initialization'. @tensorflow-models/speech-commands 0.5.4 (last published 2023) recognises an offline 18-word vocabulary (zero to nine, up, down, left, right, go, stop, yes, no), supports in-browser transfer learning, and loads its model from storage.googleapis.com by default. vosk-browser was last published in 2022.
  => Ship no wake word by default. Offer an optional 'Hey Byways' wake word through Porcupine using a user-supplied AccessKey (the user said they can enter keys), stored only on the device. Optionally add an offline micro-vocabulary fallback (self-hosted speech-commands model) for browsers without SpeechRecognition. Picovoice licence terms and any online key check are unverified.
- [verified] WCAG 2.2 SC 2.2.2 Pause, Stop, Hide (Level A): auto-updating information that starts automatically and sits alongside other content needs a way to pause, stop or hide it, or to control the update frequency. Moving content lasting more than 5 seconds needs pause, stop or hide. The Understanding document says that stopping only while the user hovers or focuses is NOT a valid pause mechanism.
  => Lean-back auto-advance always shows a visible Pause/Play button and accepts the voice command 'pause' and the K/Space key. Pausing on hover, focus or touch is an extra, never the only control. The advance interval is user-adjustable.
- [verified] WCAG 2.2 SC 2.2.1 Timing Adjustable (Level A): for each time limit, the user can turn it off, adjust it over a range at least 10 times the default, or extend it (with a 20-second warning, at least 10 times). The Understanding document says carousels and repeating scrolling text are handled under 2.2.2 because they have controls.
  => To be safe, meet both: auto-advance can be turned off before it starts (settings and first-run), and the interval slider covers at least 10 times the default (for example default 20 s, range 5-300 s, or 'wait for me'). The countdown also pauses while the app is reading aloud.
- [verified] WCAG 2.2 SC 1.4.2 Audio Control (Level A, non-interference): audio that plays automatically for more than 3 seconds needs a way to pause or stop it, or a volume control independent of the system volume.
  => Read-aloud (on by default) needs a visible Stop/Mute control on every screen, the voice command 'stop' or 'quiet', the Esc key, and an in-app speech volume and rate setting. Because this criterion applies to the whole page, missing it fails the entire page.
- [verified] WCAG 2.2 SC 2.5.3 Label in Name (Level A): a control's accessible name must contain its visible label text, ideally at the start. The Understanding document says speech-input users speak visible labels, and a mismatched hidden name 'may function as a hidden command that can be accidentally activated'.
  => Make the in-app command words exactly the visible button labels (Next, Back, Like, Skip, Save, Read it, Open, Play, Search, Pause, Stop listening). An aria-label may only extend the visible text and must start with it. This keeps OS voice control (Voice Access, Voice Control) and Byways' own commands consistent.
- [verified] WCAG 2.2 SC 2.1.4 Character Key Shortcuts (Level A): single-character shortcuts must be able to be turned off, remapped to include a modifier key, or be active only on focus. The Understanding document warns that speech-input dictation triggers them.
  => If single keys (N, B, L, S, K, Space) control Stumble, add a 'Single-key shortcuts' on/off setting, and ignore those keys while a text field has focus.
- [verified] WCAG 2.2 SC 4.1.3 Status Messages (Level AA): status messages must be exposed through role or properties (for example role=status or aria-live) so assistive technology can announce them without moving focus.
  => Use one polite live region (role=status) for 'Now showing: <title>', 'Saved to <collection>', 'Listening paused' and 'Next find in 10 seconds' (announced once, not every second). Use assertive only for errors such as 'Microphone blocked'. When built-in read-aloud is on, do not also send the same text to the live region; offer a 'Screen-reader mode' that does the reverse.
- [verified] Related WCAG 2.2 criteria: 2.3.1 Three Flashes or Below Threshold (A); 2.3.3 Animation from Interactions (AAA: motion triggered by interaction can be disabled; it notes parallax and vestibular disorders); 3.2.5 Change on Request (AAA: changes of context only on user request, or a way to turn them off); 2.2.4 Interruptions (AAA: interruptions can be postponed or suppressed).
  => Byways' own UI never flashes and has a motion toggle. Auto-advance never opens new tabs, windows or pages on its own (opening a find is always an explicit 'open' or 'play'). Auto-playing third-party embeds such as Archive games never start without an explicit 'play'.
RISKS:
- The web search budget was used up on the first query, so no official Chrome, Mozilla, Apple, Android or W3C pages could be read directly. All verified items come from package contents: MDN browser-compat-data 8.1.8, webref IDL, the W3C WCAG JSON, and plugin source. Several behaviour claims stay 'likely' or 'unverified': Chrome's speak() user-activation rule, session timeouts, the 15-second cutoff, extension mic prompts, and Android background mic rules. A follow-up message can resume searching.
- Firefox 160 (dated 2026-11-10) was still beta in the BCD snapshot. Whether it recognises locally or in the cloud, and whether it works in extension pages and sidebars, is unknown.
- Android WebView SpeechRecognition has conflicting evidence (BCD says supported; practice says unreliable). The spec forces a native bridge, so this only matters if someone tries the web path.
- In the Android-browser PWA (Chrome Android, Samsung Internet), voice runs in the cloud only (no processLocally), has no continuous mode and beeps on every restart. Always-on listening there will be poor and will send audio off the device, so 'hands-free by default' realistically means read-aloud, auto-advance and tap-to-talk there.
- The web cannot be fully zero-touch: speech output (and likely the mic prompt) needs one user activation per page load. Only the Android app can start hands-free with no touch.
- On-device language-pack size, whether install() needs user activation, and which languages Chrome or Edge desktop offer on-device are all unknown. Edge's real backend (Azure component) may not honour processLocally.
- Always-on listening drains battery and can capture other people's speech. Friends using shared builds need clear disclosure and an easy off switch.
- Built-in read-aloud can collide with screen readers (double speech). Screen readers cannot be reliably detected, so a manual 'Screen-reader mode' is needed.
- Picovoice AccessKey licence terms and whether Porcupine checks the key online are unverified. The speech-commands model loads from Google storage unless self-hosted.
- A GitHub Pages origin (iteatsthesalt.github.io) is shared by all of the account's Pages sites, so the microphone grant and storage are shared too.
RECS:
- Build one VoiceEngine interface in the shared core: start, stop, onCommand, onState and speak/cancel, with three backends. Web Speech: on-device first (available, then install, then processLocally=true, quality 'command', phrases bias), with cloud only after explicit opt-in. Native Android bridge: SpeechRecognizer plus TextToSpeech through a JS interface. 'None': keyboard, headset and tap only. Pick the backend with a functional test, never by user-agent.
- Make 'hands-free on by default' a state machine: Idle, then a single 'Start' press, then Listening and LeanBack. That one press unlocks speech, requests the mic, acquires the wake lock and starts auto-advance. On Android 13+ the native app may enter Listening straight away. Remember the user's choice, but still require the one press per launch on the web.
- Keep the command vocabulary short and match it to the visible labels (WCAG 2.5.3): next / next one, back / go back, like, skip, save / save it, read it, open, play, pause, resume, stop (reading), search for <words>, rabbit hole / more like this, stop listening. Match the whole final utterance after trimming filler words. Never fire a command found inside a longer sentence, except 'search for' which takes the rest of the sentence.
- Avoid accidental triggers: act only on final results (interim results only for 'stop' and 'pause'); stay half-duplex while the app is speaking; play a short earcon and show a caption on every recognised command; give reversible actions (like, save, skip) a 5-second 'undo'; ask for confirmation of anything destructive (deleting a collection) by voice or tap; auto-stop listening after 10 idle minutes, with an announcement.
- Offer three listening modes in settings: 'Always on while Byways is open' (default only where an on-device engine is available), 'Push or tap to talk' (default on Android browsers and for cloud engines; also on Space or a headset button), and an optional 'Wake word (Hey Byways)' through Porcupine with a user-supplied key. Always show a visible 'Listening' indicator plus a one-tap 'Stop listening'.
- Lean-back auto-advance: show each find, read the title and a one-line blurb aloud, wait the dwell time (default 20 s, adjustable 5-300 s, or 'wait for me'), then advance. Pause the countdown during read-aloud, while any panel or embed is open, while a game or emulator runs, on any touch, key or voice input (resuming only on explicit 'resume' after a game or embed), and when the page is hidden. Always show a Pause/Play button. Announce 'Next find in 10 seconds' once through the polite live region.
- Read-aloud: queue one sentence per utterance, prefer local voices (localService or not isNetworkConnectionRequired), implement pause as cancel plus resume at the sentence index, load voices with getVoices, voiceschanged and polling, and provide a Stop/Mute button, Esc and 'stop' on every screen (WCAG 1.4.2). Provide speech rate, volume and voice pickers.
- Android wrapper: require API 33+ for continuous hands-free (EXTRA_SEGMENTED_SESSION with EXTRA_AUDIO_SOURCE from an app AudioRecord; on-device recogniser with EXTRA_PREFER_OFFLINE and EXTRA_BIASING_STRINGS); use a restart loop or tap-to-talk below that. Add RECORD_AUDIO, <queries> for android.speech.RecognitionService and android.intent.action.TTS_SERVICE, run recogniser calls on the main thread, stop in onPause, use a native MediaSession for headset buttons, and use FLAG_KEEP_SCREEN_ON in lean-back.
- Extension: host voice only in the side panel (Chrome/Edge) or sidebar (Firefox), or a Byways tab. Use a one-time 'Enable voice' tab for the mic grant. The toolbar Stumble button and a chrome.commands shortcut act as push-to-talk or next. Use chrome.tts from the worker only on Chrome. Never listen while the panel is closed.
- Map Media Session nexttrack, previoustrack and play/pause to next, back and lean-back toggle while read-aloud is active. Request a Screen Wake Lock in lean-back. Respect prefers-reduced-motion and give an in-app motion toggle (WCAG 2.3.3), with no flashing UI (2.3.1).
- Accessibility checklist for the spec: one polite plus one assertive live region (4.1.3); no duplicate live-region text while built-in read-aloud is on, plus a 'Screen-reader mode' toggle; a setting to turn single-key shortcuts on or off (2.1.4); auto-advance that can be turned off before first use and adjusted over 10 times the default (2.2.1/2.2.2); no auto-opening of tabs or embeds (3.2.5); visible focus; a voice-command help card listing exactly the on-screen labels.
- Privacy copy: state which engine is active ('On-device' vs 'Google/Apple/Microsoft cloud'), that cloud voice is opt-in, that no audio is stored by Byways, and that the mic grant applies to the whole iteatsthesalt.github.io origin. Before release, re-check the items marked likely or unverified (speak() activation rule, extension mic prompts, Firefox 160 behaviour, WebView) on real devices.
