# Byways 05: AI Search and AI Team Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let people add their own AI keys, test them, pick a model, and run AI Search with one model or an AI team, with grounded links only, hard cost caps and a visible cost line.

**Architecture:** Every provider goes through a small `fetch` adapter in `src/core/ai/adapters/` (no vendor SDKs). A data table (`providers.js`) says how to reach each provider. `search.js` builds a brief, plans the run against the caps (`cost.js`), runs one adapter or the team (`team.js`) under a shared spend meter, drops every link the provider's own search metadata does not hold (`grounding.js`), and injects the finds into the engine. The UI adds Settings → AI and a first-run AI step. Plan 02's card and Stumble view already show "Found by", "Team pick" and the note that carries the cost line; Plan 05 only fills those fields, and sets Plan 02's Rabbit Hole AI hook.

**Tech Stack:** JavaScript ES2022 modules, no framework, no bundler. `node:test` for unit tests, `@playwright/test@1.63.0` (Chromium) for end-to-end tests. Web Crypto (`crypto.subtle`) for PKCE and the passphrase lock.

**Spec:** `docs/superpowers/specs/2026-11-11-byways-design.md` (§12 all, §5.6 step 4, §15.1 AI rows, §21 items 2–3). Research notes: `docs/superpowers/specs/byways-research/claude-browser.md`, `other-providers.md`, `critic.md`. Shared contract: `docs/superpowers/plans/2026-11-11-byways-00-overview.md`.

## Global Constraints

- Every rule in the overview's "Global constraints (every plan)" and "Working conventions" applies. The lines below are the ones that bite this plan.

- Claude refusal fallback (§12.3 "Server-side fallback", and the contract): requests for the models in the Claude row's `fallbackModels`, the claude-api reference's list (`claude-opus-5-5`, `claude-sonnet-5-5`, `claude-fable-5-2`, `claude-mythos-5-2`, `claude-fable-5-1`, `claude-mythos-5-1`, `claude-opus-5`; the reference says each Mythos model refuses and falls back as its Fable twin does, and Haiku 5.5 has no server-side fallback), add `fallbacks: 'default'` and `anthropic-beta: server-side-fallback-2026-07-01`. A refusal that still comes back follows §12.3: "say the model declined and suggest another model."
- Claude body: `output_config.effort` set to `low`; adaptive thinking; "**no** `temperature`, `top_p` or `top_k`, which return a 400 on this API version." (§12.3)
- Claude tools (§12.3, with the contract's per-model rule): `web_search_20260209` with `max_uses: 3` for the models the claude-api reference lists for that version (the Claude row's `webSearch20260209`), plus `allowed_callers: ['direct']` when the model's `capabilities.code_execution.supported` is false; any other model, Haiku 5.5 included, gets the basic `web_search_20250305` with `max_uses: 3` and no `allowed_callers`; `report_finds` with `strict: true`, `additionalProperties: false`, and `tool_choice: auto`.
- "On `pause_turn`, send the paused content back with the same tools and the `container` id, at most 5 times." (§12.3)
- Cost: "`usage.server_tool_use.web_search_requests × $0.01`, plus tokens times the model price. Prices per million tokens (input/output): Opus 5.5 $4/$20, Sonnet 5.5 $2/$10, Haiku 5.5 $0.10/$0.50." (§12.3)
- "A link from AI is shown only if **all** of these are true": it is in the provider's own search metadata, and it is `http(s)`, not blocked, not already seen, and passes the liveness check. (§12.4)
- Gemini: "Native `generateContent` with `google_search`, then a second call that formats the result as JSON. Never the OpenAI-compatible endpoint." (§12.2)
- OpenRouter: "The `openrouter:web_search` tool (engine `auto`, `max_results 5`, `max_uses 2`)." (§12.2)
- Team: `Promise.allSettled`; "45 s for members that search and 20 s for the Captain"; merge "by normalised URL (§14.1)"; the Captain "returns `{order:[candidateId], why:{id:text}}` with a strict schema, and may only reference ids it was given." (§12.6)
- Caps: "$0.50 by default and adjustable" per run; "50 searches per provider per day"; "$2.00 a day in total, adjustable"; "AI results are cached per query for 7 days"; unknown prices show "price unknown". (§12.7)
- Keys: "A key is sent only to its own provider's host." "AES-GCM, using a key derived by PBKDF2-SHA-256 (600,000 iterations)." Never in exports (unless chosen), share links or logs. (§12.8) Every request that carries a key is host-checked and refuses redirects (Task 2).
- §15.1: AI calls go "Only [to] the providers you set up, with your query, your tags and recent domains."
- Model identifiers appear only in `providers.js`, `models.js`, their tests, fixtures and the copy that shows them as data. Never in commit messages or code comments.
- Strict tool schemas may not use `minLength`, `maxLength`, `minItems`/`maxItems` or numeric bounds (claude-api reference: strict mode rejects them). Limits are stated in `description` text and enforced in `cleanFinds`.

## Review Focus

1. **Near-miss URLs from the model.** A model reports `https://WWW.Example.org/a/?utm_source=x#top` while search returned `https://example.org/a`. A person expects the find kept, and a link that only the model claims to know dropped. Pinned by `filterGrounded matches by normalised URL and drops ungrounded links` (Task 5).
2. **Hostile text in search results.** A result title holds `<img src=x onerror="window.__xss=1">Tiny Museum` and a 900-character "why". A person expects the markup reduced to the text `Tiny Museum` (never rendered as HTML), the "why" cut to length, and no `javascript:` link. Pinned by `cleanFinds cuts lengths, filters tags and drops non-http urls` (Task 4) and the e2e `AI find text renders as plain text` (Task 19).
3. **Repeated paid searches.** Hands-free "search for …" repeated, or the same query typed twice. A person expects the second identical query to cost nothing, and the day's searches to stop at 50 even when a run starts at 49. Pinned by `aiSearch serves a repeated query from the 7-day cache with no network`, `a run that starts at 49 searches sends max_uses 1` and `aiSearch stops at the daily search cap` (Task 16).
4. **A key sent to the wrong host.** A custom base URL, a stored address for a built-in provider, or a 30x redirect points somewhere else. A person expects the key never to leave its provider's host. Pinned by `aiFetch refuses to send a key to another host`, `a Bearer key to another host is refused`, `keyed requests refuse redirects` and `mapAiError never repeats key text from the body` (Task 2), and `keyHostOk allows only the provider host` (Task 1).
5. **Keys locked at search time.** The passphrase lock is on and the app was reloaded. A person expects "Unlock your keys in Settings → AI to search." and keyword search instead, with no provider call. Pinned by `aiSearch with a locked keyring makes no provider call` (Task 16).

`costOf` is `(in × inputTokens + out × outputTokens) / 1e6 + searchUsd × searches`. `planRun` runs three steps and collects their notes. (3) `budget.canRun(fit.estimateUsd + estimateRun(extra), providers)`. `fitToCap` works on copies, in two phases. Phase 1: while the total is over the cap and some member has `maxUses > 1`, take one search from the member with the highest estimate among those. Phase 2: while still over and more than one member is left, drop the member with the highest estimate. If one member at 1 search is still over, return `ok: false` with the reason in the test. Notes keep one line per member, in order of its first change, with the member's final value. Role labels are `Scout`, `Digger`, `Wildcard`, `Captain`; a member with no role gives "Lowered searches to N to stay under the $X cap." Caps print with `toFixed(2)`. `canRun` checks the spend cap first, then each provider's search count against `settings.ai.dailySearchCap`.

- [ ] **Step 3: Implement `src/core/keys.js`**

`ready` reads `__lock` and sets `locked` when it exists. `__lock` is `JSON.stringify({v:1, kdf:'PBKDF2-SHA-256', iterations:600000, salt, iv, check})`, all base64, where `check` is the AES-GCM ciphertext of `byways-keyring`. A 16-byte random salt is made once per `enableLock`; each value gets a fresh 12-byte iv and is stored as `enc1:<iv b64>:<ciphertext b64>`. The derived `CryptoKey` (non-extractable, AES-GCM 256) lives only in a closure variable; `lock()` clears it. `unlock` returns `false` when decrypting `check` throws. `get` returns `null` for an `enc1:` value while locked; `set` rejects with `Error('Keyring is locked')`. `enableLock` encrypts every stored value that is not already `enc1:`; `disableLock` checks the passphrase, writes plaintext back for the `enc1:` values and deletes `__lock`. Use `crypto.subtle`, `crypto.getRandomValues`, `btoa` and `atob` (all present in Node 22 and browsers).

- [ ] **Step 3: Implement `src/core/ai/adapters/anthropic.js`**

Every request goes through `aiFetch` (Task 2) with the four §12.3 headers. When `model` is in the row's `fallbackModels`, the body adds `fallbacks: 'default'` and the headers add `anthropic-beta: server-side-fallback-2026-07-01`: the server re-runs a declined request on the model Anthropic recommends for that refusal category. The search tool is chosen per model too (contract): a `model` in the row's `webSearch20260209` gets `{type: 'web_search_20260209', name: 'web_search', max_uses}`, plus `allowed_callers: ['direct']` when `modelInfo?.codeExec === false`; any other model gets the basic `{type: 'web_search_20250305', name: 'web_search', max_uses}`, which has no dynamic filtering and so no `allowed_callers`. `listModels` sends the same headers, `anthropic-beta` included, so **Test connection** also proves that this header passes CORS from each version (claude-browser.md: the preflight echoes every requested header). No `temperature`, `top_p` or `top_k` is ever set. `listModels` keeps a model when it is `active` and its capabilities support `server_tools.web_search`, `thinking.types.adaptive` and `effort.low` (every request sends all three); `name` is `display_name`. `complete` sends one request with `output_config: {effort: 'low', format: {type: 'json_schema', schema}}` and no tools, under the same fallback rule.

**Cost of one response** (claude-api reference, refusal fallbacks): price by `res.model`, the model that answered. When `usage.iterations` holds a `fallback_message` entry, the tokens are the sum over `usage.iterations`; entries before the first `fallback_message` ran on the requested model (a declined attempt, counted so the caps stay an upper bound) and the rest on `res.model`. Otherwise the top-level `usage` at `res.model`. Searches are `usage.server_tool_use.web_search_requests`. `unknownPrice` is true when a model that ran has no exact price. Each response's `content` is echoed back unchanged, `fallback` blocks included and in place: requests are not streamed, so a mid-output decline leaves no partial content to strip.

The loop, which the tests do not fully fix:

```
messages = [{role:'user', content: briefText(brief, role)}]; container = null
continuations = 0; pendingRounds = 0; nudged = false
loop:
  if meter?.over → throw AiError cap
  res = POST body(messages) + (container ? {container} : {})
  add res's cost and usage to the totals and the meter; container = res.container?.id ?? container
  for each web_search_tool_result block: Array content → add each result url; object content → push error_code to searchErrors
  if res.stop_reason == 'refusal' → throw AiError refusal (the fallback chain declined too)
  if res.stop_reason == 'max_tokens' → throw AiError incomplete   // a cut-off report_finds input still parses
  if res.stop_reason == 'pause_turn':
     if continuations == 5 → throw AiError incomplete
     continuations++; messages.push({role:'assistant', content: res.content}); continue   // no extra user turn
  report = the tool_use block named report_finds, if any
  if report:
     pending = a server_tool_use id that no *_tool_result block answers (by tool_use_id)
     if pending and pendingRounds < 2:
        pendingRounds++; push assistant content; push user [tool_result toolu_id PENDING_REPLY]; continue
     return result(cleanFinds(report.input, {tagIds: brief.tagIds}), model: res.model)
  if !nudged: nudged = true; push assistant content; push {role:'user', content: NUDGE}; continue
  throw AiError no-finds
```
